# Изолированный benchmark massCode

Первый сценарий: **1000 Code + 1000 Notes + 1000 HTTP** (3000 записей).
Применяются реальные API handlers и serializers vault. Обычный профиль и уже запущенное приложение не используются. Подготовка создаёт отдельные production build, профиль и vault; существующий output отклоняется. Нужны установленные зависимости и Electron текущего проекта.

```sh
# Быстрый smoke: 10 записей суммарно (6/3/1)
pnpm bench:prepare --count 10
# Полный первый набор: 1000 в каждом пространстве
pnpm bench:prepare --space all --count 1000
# Используйте абсолютный output, напечатанный prepare
pnpm bench:start --output /absolute/run
pnpm bench:report --output /absolute/run
```

По умолчанию output — уникальный игнорируемый `docs/benchmarks/<run>`. `--output` позволяет выбрать новый каталог. `--seed` задаёт детерминированный контент. `--port` задаёт отдельный API порт (54321 по умолчанию): при конфликте выберите новый run с другим портом. `--space mixed` (по умолчанию) распределяет общее `--count` примерно 60/30/10%; `code`, `notes`, `http` создают одно пространство. Только `all` трактует count как число **на пространство**.

Code содержит по три фрагмента; тексты разных размеров (512/4096/32768 символов основы), notes содержит Markdown и fenced code, HTTP — JSON и локальный POST `http://127.0.0.1:5191/echo`. Для Send предварительно запустите `pnpm http:server`. Генерация проверяет контент каждой записи и итоговые количества. `seed.json` содержит размеры и SHA-256 содержимого; UUID и времена хранения зависят от запуска.

## Ручной протокол через Computer

1. Зафиксируйте ОС, нагрузку, режим питания и параллельно работающие приложения вместе с manifest.json. Окно теста имеет название `massCode BENCHMARK`. На macOS первый start создаёт отдельную копию Electron в `<run>/runtime/massCode Benchmark.app`, меняет только её bundle identity и подписывает ad-hoc через системный codesign. Для Computer выбирайте этот полный путь: он отделяет тест от уже запущенного dev-приложения. Копия требует дополнительного места на диске.
2. Проверяйте дерево HTTP также по скриншоту: виртуализированные строки могут отсутствовать в текстовом accessibility tree Computer. Запустите профиль; откройте Code, Notes, HTTP. Измерьте первое открытие списка и первой записи. Повторите открытия минимум 20 раз для p95; сохраните размер выбранных документов в ручных заметках протокола.
3. В Code/Notes ищите `needle`: первая поисковая загрузка в сессии, новые строки поиска и повторы той же строки разделены. HTTP sidebar фильтрует локально и имеет отдельную метрику. Search-first/new/repeat обозначает историю строк запросов только в памяти renderer, а не гарантированное состояние индекса/кэша.
4. Повторный запуск процесса допустим на том же профиле. Он сохраняет UI state и изменения. Для полностью исходных данных создайте новый output тем же seed. Автоматического удаления/restore нет. Кэш ОС не очищается, поэтому запуск после рестарта не называйте cold-disk benchmark.
5. Закройте только тестовое окно обычным выходом приложения, затем сформируйте отчёт. События также сбрасываются раз в секунду, но последний неполный интервал при аварийном завершении может потеряться.

## Что измеряется

- `startup.main-imported`: bootstrap до импорта main; `startup.renderer-document-loaded`: bootstrap до did-finish-load, не до готовности всех редакторов.
- `api.<domain>.<method>.<list|item|other>`: main bridge fetch и чтение response body; без renderer IPC transfer и paint. IDs, query и содержимое не записываются.
- `*.state-presented`: загрузка/присвоение состояния, Vue nextTick и следующий requestAnimationFrame. Это **не доказательство завершения paint**; debounce ввода поиска до вызова загрузчика не входит. Устаревшие результаты и ошибки имеют отдельный статус.
- `elapsedMs` в событиях и снимках памяти: время от bootstrap данного процесса до регистрации события в main. Позволяет отделить длительность операции от её места на шкале запуска; задержка IPC тоже входит. Это не время от клика по иконке приложения.
- `memory.jsonl`: process tree Electron при загрузке документа, первом успешном list/open и первом успешном поиске каждого пространства; memory в единицах Electron (KB). Сравнивайте `workingSetSize` каждого процесса отдельно. Сумма — приблизительная оценка: общие страницы могут учитываться несколько раз; пиковые значения процессов нельзя складывать как одновременный пик.

Статус `ok` подтверждает завершение операции без исключения, но не полноту данных: отдельно проверьте ожидаемое число записей и содержимое интерфейса. Пустой provisional-список нельзя считать готовой библиотекой.

Отчёт показывает n, медиану, максимум, p95 только при n ≥ 20. Не смешивайте разные размеры данных/условия в одном выводе. Это пилот, а не маркетинговый предел вместимости. Save durability, end-to-end Send и отрисовка сложных документов требуют отдельного протокола и пока не измеряются. CPU первого поиска можно исследовать отдельным запуском ниже.

Инструментирование выключено без валидного marker и изолированного профиля. Данные renderer принимаются только от доверенного main frame и по списку разрешённых метрик. Обновления и регистрация системного протокола отключены только для валидного benchmark запуска. Сбор использует секундный буфер; накладные расходы присутствуют и должны учитываться при сравнении.

Проверка утилит: `pnpm exec vitest run scripts/benchmark/common.test.ts`.

## Профиль первого поиска и поиска после правки

Закройте тестовое приложение и дождитесь окончания генерации. Запускайте проходы последовательно, каждый в новом процессе Electron:

```sh
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --label current-1
# Для A/B передайте скомпилированный searchIndex.js предыдущей версии
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --label baseline-1 --tokens /absolute/baseline/build/main/storage/providers/markdown/runtime/shared/searchIndex.js
```

Профилировщик использует build выбранного run. После изменения исходников пересоберите main в `<run>/build` через `pnpm exec tsc -p tsconfig.main.json --outDir /absolute/run/build`. Сохраните старую сборку до пересборки, если она нужна для A/B. `--tokens` заменяет только функцию токенизации; остальные части сборки остаются одинаковыми. Используйте только собственную локальную сборку. Результат `search-<label>-<time>.json` содержит путь и SHA-256 модуля токенизации.

Проверяются Code и Notes: первый поиск по `needle`, повтор, точное имя, отсутствие совпадений, поиск после изменения тела одной записи и его повтор. Число результатов сверяется с seed. Тестовая правка восстанавливается в `finally`, но время изменения записи обновляется; при аварийном завершении процесса восстановление не гарантируется. Запускайте только на disposable benchmark vault, без параллельного приложения на этом профиле.

Замер начинается после фоновой сверки библиотеки. `hydrate` включает догрузку, `readFiles`, `parseFrontmatter` и `parseFragments` вложены в неё — их нельзя суммировать как независимые этапы. `index` — синхронное построение индекса, `query` — запрос к нему. В сборке с обработкой порциями `prepareAsync` включает гидрацию, индексацию и ожидание между порциями; `updateIndex` включает добавление документов в приватный индекс. `hydrateItem` — догрузка отдельных заметок (вложена в `hydrate` для синхронного пути). Эти фазы также перекрываются и не суммируются. Таймер, поставленный перед API-вызовом, показывает задержку event loop главного процесса; это не время отрисовки или задержка ввода. Renderer в этом протоколе не запускается. Сравнение не заменяет UI-проверки через Computer.

Первый проход после генерации считайте подготовительным: первоначальная сверка может прочитать тела и построить индекс ещё до поискового запроса. Не смешивайте его с проходами, где первый поиск сам выполняет индексацию; сверяйте фазовые тайминги.

Для диагностического A/B чередуйте порядок старой и новой версии минимум в трёх проходах. Не запускайте параллельно генерацию данных или другие нагрузочные тесты. Проверяйте отдельно разнообразный контент: повторяющиеся строки текущего seed благоприятны для дедупликации слов и не представляют все пользовательские библиотеки.

### Сравнение изменений всего поискового runtime

Для изменений алгоритма обновления индекса одного `--tokens` недостаточно. До пересборки сохраните каталоги `main` и `shared` из `<run>/build` в `<run>/search-baseline`, затем используйте полную исходную сборку:

```sh
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --build /absolute/run/search-baseline --label before-1
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --label after-1
```

Путь сборки фиксируется в `buildRoot`. Отдельная строка `edit` измеряет изменение тела через API; сравнивайте её вместе с `after-edit`, чтобы не принять перенос работы из поиска в сохранение за ускорение. Это время API, без гарантии завершения отложенной записи на диск. Перед правкой кешируется отсутствие тестового слова; после правки проверяется один результат, после восстановления — снова отсутствие. Так проверяется и очистка кеша поисковых результатов.

Опция `--record-index 998` выбирает созданные генератором `bench-code-000998` и `bench-notes-000998` для правки. Это позволяет отдельно проверить большой документ (индексы с остатком 2 при делении на 3 имеют основу 32 768 символов). Без опции выбирается первая запись списка. Длина редактируемого содержимого фиксируется в `editedContentChars`.

### Отзывчивость первого поиска и CPU

```sh
# Диагностика CPU отдельно от контрольных замеров времени
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --label cpu-current --cpu
```

`--cpu` сохраняет отдельный `.cpuprofile` для первого поиска Code и Notes. Профиль можно открыть в совместимом просмотрщике V8 CPU profiles. Профилирование добавляет накладные расходы: не включайте эти проходы в обычное A/B-сравнение времени.

Каждый API-замер также содержит:

- `timerDelayMs`: время до первого таймера после начала операции.
- `maxEventLoopDelayMs`: максимальное превышение интервала heartbeat (10 мс), включая незавершённый интервал в конце операции. Это диагностическая оценка задержки главного процесса, не задержка ввода или отрисовки.
- `heartbeatTicks`: сколько раз heartbeat получил управление во время операции. Для короткой операции ноль нормален; для многосекундной указывает на отсутствие обслуживания этого таймера.
- `memoryBefore`, `sampledPeakRss`, `sampledPeakHeapUsed`: память главного процесса до операции и наибольшие наблюдённые RSS/heap. Выборки снимаются перед операцией, на heartbeat и в конце. Промежуточный пик внутри синхронного участка может быть пропущен; renderer и остальные процессы Electron не входят.

При обработке порциями оценивайте вместе полное время запроса и максимальную задержку heartbeat: отдача управления может улучшить отзывчивость без ускорения завершения поиска. Бюджет порции не гарантирует верхнюю границу задержки — один документ, файловая операция или сборка мусора могут занять больше. Для сравнения используйте полные сборки через `--build`, одинаковый vault и минимум три чередующихся прохода каждой версии.

## Запуск и память большой библиотеки

Проводите минимум три запуска нового процесса с одинаковым сохранённым пространством и выбранной записью. Сохраняйте номера `session`: общий отчёт объединяет события разных запусков, поэтому для времени старта используйте `elapsedMs` нужной сессии. Проверяйте появление полного списка и содержимого записи через Computer; `did-finish-load` и ранний пустой список не означают готовность библиотеки.

Отдельным проходом откройте Code → Notes → HTTP и выполните первый поиск в Code и Notes. Снимки памяти после поиска включают тела документов и поисковые индексы. Рост RSS сам по себе не доказывает утечку; для этого нужны повторные циклы и проверка удерживаемых объектов.

Для матрицы масштаба повторите протокол на 1 000 и 10 000 записей **в каждом** пространстве. Измерьте запуск отдельно с сохранёнными Code, Notes и HTTP, выбрав сопоставимые по размеру документы. Новый процесс не означает холодный файловый кеш ОС. Указывайте число повторов, выбранный документ, фоновые проверки и фактическое число записей, включая остатки QA. При трёх повторах приводите медиану и диапазон, а не p95.

Фоновая миграция старых вложений Notes пропускает чтение тел заметок, когда `notes/assets` отсутствует или пуст. После этого первый поиск может включать больше работы по загрузке заметок, чем в старой сборке. Сравнивайте старт и первый поиск вместе; при повторном поиске тела и индекс уже могут находиться в памяти. Непустой каталог старых вложений — отдельный сценарий, в котором миграция по-прежнему нужна.

При диагностике пауз учитывайте автоматический Vault Doctor: он запускается после сверки пространства с диском. Preview обрабатывает файлы порциями с передачей управления между ними; обход каталогов, чтение одного файла и заключительная обработка отчёта всё ещё могут превышать бюджет порции. Полное время аудита и максимальная пауза главного процесса — разные метрики. Применение исправлений остаётся синхронным, чтобы операции записи не перемежались с другими изменениями.

## Память поискового индекса

```sh
# Отдельный диагностический проход; не смешивать с контрольными таймингами
pnpm exec electron scripts/benchmark/search-profile.cjs --output /absolute/run --label heap-current --heap
```

`--heap` включает sampling heap profiler на первом поиске каждого пространства и сохраняет `.heapprofile` с местами выделения ещё живых объектов. Это выборочный профиль, не полный heap snapshot. Перед первым поиском и после него инструмент принудительно запускает GC; `heapProfiles[].retainedMemory` содержит память main process после этого GC. В обычном приложении принудительный GC не добавляется.

Code и Notes исследуются последовательно: снимок после Notes включает также индекс Code. Эти значения нельзя складывать. Renderer и остальные процессы Electron сюда не входят. Для обычных времени и наблюдаемого пика RSS делайте отдельные проходы без `--heap` и `--cpu`.

Индекс хранит нормализованные части документа с исходными разделителями вместо дополнительной склеенной строки. Если нормализация не меняет текст, V8 может переиспользовать исходные строки; для текста, требующего изменения регистра/диакритики, выигрыш может быть меньше. Фразы через границы частей проверяются по коротким фрагментам около разделителя, включая несколько пустых частей. Семантика поиска подстроки сохраняется.

Для сравнения этой оптимизации используйте `--build`: изменение затрагивает и представление текста, и движок. Режим `--tokens` совместим со старым строковым tokenizer через склейку частей пробелом только для токенизации; эта диагностическая склейка добавляет накладные расходы и не подходит для оценки памяти нового представления.
